# RCA — Alta Pulse (privacy-agent-hub) deploy failure

**Run:** ba661cd6-5572-4f08-9d92-a5de4a91ebbc (redeploy, agentic)
**Failed step:** pull_source (prepare build context → "update python dependencies: run pip freeze")
**App:** privacy-agent-hub / altapulse.com.br — FARM template, Cloudflare frontend, tier_0
**Live app is unaffected:** the previous successful run (bbd0a32b) is still active and serving. Nothing rolled back; the new code simply never got past staging.

## Symptom
pull_source died ~17s in. All later steps (mongodb_migrate, manage_secrets, deploy, health_check) show "not run: an earlier deploy step failed." No source zip was uploaded (eph sandbox returns eph_source_missing), so build_image never ran.

```
prepare build context: update python dependencies: run pip freeze:
failed to execute pip freeze: command terminated with exit code 1, stderr:
Traceback (most recent call last):
  File "/root/.venv/bin/pip", line 10, in <module>
    sys.exit(main())
  ...
  File "<frozen importlib._bootstrap_external>", line 729, in _compile_bytecode
EOFError: marshal data too short
```

## Root cause
pip itself cannot start inside the **preview pod's** venv (`/root/.venv`). `EOFError: marshal data too short` while importing pip's own modules means a `.pyc` bytecode file is **truncated/corrupt**. The standard cause of a truncated `.pyc` is a write that was cut off because the **filesystem ran out of space** mid-write.

This matches the known preview-environment state:
- `/app` is at **99%** (9.8G total, ~109M free).
- `.git` alone is **7.6G**, driven by committing a full ~260MB Electron installer set (`backend/desktop_dist`) on every release **plus a tracked 201MB Node distribution in `desktop-tools/`**.
- 5.73GiB of that is loose git objects that could not be repacked for lack of free space.

With the disk this full, Python's bytecode write for pip got truncated, leaving a corrupt `.pyc`; every subsequent pip invocation (including pull_source's `pip freeze`) now fails on import. Earlier runs today succeeded, so this corruption was induced recently as the disk crossed its ceiling.

This is **preview-pod infrastructure corruption driven by repo bloat** — not a source-compile error and not a deployment-manifest (Dockerfile/entrypoint/nginx/config.yaml) issue. pull_source's `pip freeze` runs on the preview pod's venv, which no manifest file controls, so there is nothing in the manifest set to edit. `resume_pipeline`/force_repull would re-run the same `pip freeze` against the same corrupt venv and fail identically.

## Fixes
### 1. Platform (immediate unblock — escalate to Emergent support)
The preview pod's venv is corrupt and its disk is exhausted. Repair is needed before any redeploy can pass pull_source:
- Recreate/repair `/root/.venv` (reinstall pip, or clear the truncated `.pyc` cache) so `pip freeze` runs, AND
- Restore disk headroom on the preview pod's `/app`.

### 2. Code / E1 (durable fix — stop the repo from re-filling the disk)
The repo bloat will re-exhaust the disk and re-break pip after any repair unless the committed binaries are removed from git:
- **Remove the tracked 201MB Node distribution in `desktop-tools/` from git** (`git rm -r --cached desktop-tools/<node-dist>`, add to `.gitignore`). It does not need to be in version control.
- **Stop committing the ~260MB Electron installer set on every release.** `backend/desktop_dist` MUST still be present in the **deployed image** (it is served by `/api/desktop/release`), so do NOT simply delete it from the build — instead either (a) generate/bundle it at build time, or (b) keep it in the working tree but out of git history, and ensure the Dockerfile copies it into the image. The problem is the *history accumulation* (every release adds another ~260MB), not the current copy.
- After untracking, run `git gc`/repack to reclaim the 5.73GiB of loose objects (may require history rewrite, e.g. `git filter-repo`, to actually shrink `.git` from 7.6G). This frees disk so pip stays intact.

### 3. User (separate, already communicated — not the blocker)
`OWNER_EMAIL` secret is still absent (RESEND_API_KEY and MAIL_FROM are present). Add it via Re-publish → Secrets before the next deploy so email features work. Note: this did NOT cause this failure — the run never reached the secrets step.
